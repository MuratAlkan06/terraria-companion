## 1. Design principles (binding)

1. **Transparent and decomposable.** Every rendered score decomposes into named components, each with its exact formula string, raw inputs, unit, weight, and weighted contribution, rendered by ScoreBreakdown. No number appears whose derivation cannot be shown in one disclosure.
2. **Data-driven, sim-independent.** All scoring reads verified record fields through getField. Scoring NEVER consumes the Lab engine or its outputs (est. DPS exists for only 149/488 weapons at P3 close-out — B115; mixing it in would punish unsimulated weapons). One uniform proxy (§2.2) ranks all weapons. Lab figures may be linked as evidence, never summed into a score (B69/Q7).
3. **Unknown is excluded and disclosed — never defaulted.** An unverified/absent required input removes that input (or component, or candidate) and increments a visible disclosure ("scored from 4 of 6 factors — 2 unknown"), unknowns named per UX §5.3. Never 0, never an average, never a substituted difficulty.
4. **Unknown gating is never obtainable.** isObtainableNow "unknown" NEVER counts as obtainable. Today dominant: gating derivable for 47/488 weapons, 23/352 accessories, 6/256 armor pieces (2/67 sets), 2/79 ammo — 1,097 gating-underived gaps. Algorithms under-recommend honestly (designed empty slots with counts), never leak.
5. **No cross-goal composite, no universal "best".** Scores exist per goal; composites only in ≥2-build comparisons, normalized relative to the compared set. Copy audit (§8.4) bans "best" and outcome words.
6. **No fight-outcome predictions.** Readiness output is factor explanations only; ReadinessFactorCard/ScoreBreakdown structurally lack verdict/probability props; no factor-level grades — factors emit tagged lines (easier | harder | info | unknown); the SummaryCard's two columns are exactly the easier/harder unions.
7. **Editorial weights are versioned constants** in `src/scoring/constants.ts`, frozen `as const`, under SCORING_CONSTANTS_VERSION; changes bump the version, re-pin goldens, add a changelog entry (B38 discipline).
8. **Deterministic.** Same inputs (+seed for Surprise Me) ⇒ identical output; all tie-breaks end in a total order (§4.6).

### 2.2 Damage-potential proxy DPP(weapon, ammo?) — the sim-free ranking stat
Required (via getField; any one unverified ⇒ weapon not scoreable): damageClass, damage, useTimeTicks, useAnimationTicks, plus critPct for melee/ranged/magic (NOT required for summon per B17/B64, nor for classless "other": classless damage never deals critical hits, so its crit is NOT APPLICABLE — not Unknown — critFactor = 1 and the tip says so, "Classless damage never deals critical hits, so none are added." (B85(b), wiki Critical hit rev 1032172; supersedes B17's "other crit Unknown")). Optional (absent = default, unverified = blocks): autoReuse (false), reuseDelayTicks (0), ammoClass.

```
cadenceTicks      = useAnimationTicks − (1 if melee && autoReuse) + (reuseDelayTicks ?? 0)   // B14 + autoswing + B48(a)
activationsPerUse = ceil(useAnimationTicks / useTimeTicks)  if ranged/magic and useTimeTicks < useAnimationTicks, else 1
hitsPerSec        = activationsPerUse × 60 / cadenceTicks
perHit            = damage + (ammo.ammoStats.damage if ammoClass and ammo in context, else 0)
critFactor        = 1 + (4 + critPct)/100    // BASE_CRIT_PCT = 4 labeled (B17); = 1 for summon (B17) and "other" (B85(b): not applicable)
DPP               = perHit × hitsPerSec × critFactor   // unrounded, labeled "est."
```
Assumptions string (verbatim in every DPP-derived AssumptionsTip): "Single target, point-blank, target defense 0, no damage variance, no reforge modifiers, one hit per melee swing, projectile/DoT side effects not counted, held-attack rate." When ammoClass present but no ammo in context: append "scored without ammo — no ammo with verified availability". On the builder-less weapon comparison (P4-S1) that string doesn't fit, so the ammo assumption reads "No ammo is chosen here, so only the weapon's own damage counts. In-game, each shot adds the damage of the ammo it fires." (B99(d)). DoT, projectile multipliers, pierce, kind:"special" are NOT in DPP v1; real uncounted effects are named in the rationale. Scoring never reads labBehavior.

**Held-attack qualifier (B101(a), B102).** The DPP number stays uniform for every weapon, but a weapon that breaks the held-attack assumption or is consumed on use carries an IN-CELL secondary qualifier line under its figure (the "Not applicable"/"Not estimated" pattern), on the comparison and the builder alike. Each part derives from ONE verified field — no category exemptions (the 110 no-auto-reuse melee weapons read "One click per attack"; the assumption genuinely breaks there):
- autoReuse verified false → "one click per throw" (consumable) / "one click per attack"; tip: "Assumes a click every {cadence} ticks — it has no auto-reuse, so holding attack doesn't repeat it."
- maxStack verified (used up as it's used) → "uses {N}/s"; tip states the usage rate.
- the wiki Explosives tag (`explosives` — not the Lab's editorial archetype; covers Scarab Bomb/Freeze) → "blast and fuse not counted".
Parts join with " · ", first letter capitalized: "One click per throw · uses 1.5/s · blast and fuse not counted". Comparison crit row (B103): hidden only when NO compared column can crit (e.g. a single classless weapon); otherwise a classless or summon column reads "Not applicable" with its reason.

### 2.4 EffectiveProgress and gating evaluation
```
EffectiveProgress(progress, stage, worldEvil) = trackedDefeated ∪ VirtualDefeats(stage, worldEvil)
VirtualDefeats(S, evil) = { n | STAGE_ORDER[n.stage] < STAGE_ORDER[S] ∧ n is a required-gate ancestor of ≥1 node with stage ≥ S }
```
Required-gate DAG only. Optional bosses are never ancestors ⇒ never assumed defeated by stage (under-recommend). World evil: EoW/BoC are never virtual — they count only through a TRACKED defeat. With a world evil chosen, only the matching node's mark counts; with none chosen ("Both", the map's setting) a tracked defeat of EITHER counts (`countsInWorld` in the shared progress module, applied app-wide incl. boss-page gear satisfaction — B96(a), B97; supersedes B69/Q6's "null ⇒ neither"). The map's cascade, the recommender and every gated surface therefore agree on what the user marked; where a "Both" nuance remains it is explained in a separate sentence, never by silently filtering (B96(a)). Milestone/event gate slugs satisfied iff all required-gate predecessors satisfied (recursive, memoized); milestones and events are derived, never markable (B86(a)).
**Scope split (binding):** Builder uses tracked ∪ virtual (stage = user hypothesis, P4-S2 AC4). Feature B's "obtainable now" uses the same tracked ∪ virtual — "the user's stated stage + tracked boss defeats", PRD Feature B AC2 verbatim; with no stage selected it is tracked-only; the plan page's "based on" note states the basis and why it differs from Feature A (B117). Feature A improvement gating uses tracked defeats ONLY (Feature A AC2) — intentional divergence (B69/Q9). Tracked-only also governs the boss map, GateBadges and the "What Should I Do Next?" recommender, where the selected stage is display context only (B89; UX_SPEC §3.7).
**Non-node conditions** (biome/event/time, no satisfiedByNode): never flip status to "gated"; ALWAYS returned in missing.conditions and rendered as requirement chips ("requires: Blood Moon") — never silently satisfied (B69/Q4).

_Amendment history (B121 sweep): B96(a)/B97 "Both" counts either evil mark (supersedes B69/Q6 null ⇒ neither); B117 Feature B scope; B89 recommender scope; B86(a)._

### 2.5 Per-way gating (Feature B way chooser — B118(f), B119)
What each listed way to get an item needs from the plan's progress basis (§2.4, Feature B scope), from verified data only (src/app/routes/plan/planRouteGates.ts):
- An item with ONE way: that way's gate IS the item's verified gatedBy (DATA_SCHEMA_SPEC §7b), so the chooser and the tree agree by construction.
- A recipe (one of several ways): the union of the recipe's node-mapped conditions and the verified gating of every ingredient and station item; an "Any X" group counts as its least-gated member (one member open ⇒ open; else any member Unknown ⇒ Unknown; else the member needing the fewest bosses — Unknown when the cheapest members need different bosses, since a single gate can't say "either"). Crafting environments are places, not gates. Any input whose gating is Unknown makes the way Unknown (known bosses still named).
- A drop (one of several ways): any one record suffices — a boss's drop or its Treasure Bag is open once that boss is defeated; any other source's gating isn't in the data (Unknown); records needing different bosses read "one of".
- A vendor, chest, fishing spot or wiki-described way (one of several): its node-mapped conditions are named, but whether the vendor/place itself is open isn't in the data ⇒ Unknown. Conservative by design: Unknown is never "obtainable now" (§1.4).
Inputs' non-node conditions return as requirement chips (B69/Q4). The chooser's counts agree with the tree's, and per-route gates are shown with linked boss/station names (B118(f)).

## 3. Candidate filtering (shared: recommendation, Surprise Me, improvements)
An item enters a slot pool iff ALL:
1. **Availability:** status "yes". "gated" ⇒ GatedSection track (§4.7) with exact missing bosses. "unknown" ⇒ excluded, counted. Owned items: unknown→eligible with "you marked this owned" rationale; gated is NOT upgraded (B69/Q2). This pool rule governs SUGGESTIONS only; the readiness analysis of the user's own loadout counts owned items whatever their gating (§6, B94(1)).
2. **Class eligibility:** weapons damageClass===C (any for hybrid); summon-slot pool = summon weapons tagged minion-summon-items; for C=summon the main pool = whips. Armor variant eligible iff C ∈ (variant.classes ?? [variant.class]); ['other'] eligible for all; hybrid matches every variant (B52 adapter).
3. **Scoreability:** every required proxy field reads verified; failures excluded + counted.
4. **Difficulty legality:** SLOT_COUNT = {classic 5, expert 6, master 7}; demonHeartSlotIndex = {classic none, expert 5, master 6}; that slot labeled "Demon Heart slot" with the assumption chip + WoF GateBadge when wall-of-flesh ∉ EP (B69/Q3; toggle deferred).
5. **World-type legality (B97(a), B108(b)):** with a world evil CHOSEN, items requiring the other world's condition (`corruption-world`/`crimson-world` in gatedBy.conditions) or gated behind the other world's evil boss are out of the modeled world (the map dims that fork) — never suggested, counted in the disclosure with the reason ("N need a Crimson world"; Improve names the boss). Under "Both" nothing is excluded for this.
**Pool disclosure (always rendered):** per slot: pool size, excluded-unknown, gated, excluded-unverified, unqualified (§4.4) and other-world (rule 5) counts; verified-obtainable and owned-Unknown counted apart ("40 verified obtainable + 1 owned (unverified)", B108(e) H3).

## 4. Loadout recommendation (P4-S2)
Inputs `{stage, class C, difficulty D, goal G, targetBossId?, owned[], progress, settings, seed?}` — all optional with defaults (stage from settings else early-prehm; C melee; D classic; G balanced).
- **Target boss (B106):** the target and every fight it opens stay OUT of the stage's virtual defeats, so their gear lands on the gated track (§4.7), whose target-boss group leads (B108(e) M1); bosses already marked defeated stay counted (matches Feature A's target-boss exclusion).
- **Stage from a link (B108(c), B109):** the comparison's "Open in Builder" passes no stage, and the builder must NOT silently default it — it opens at Step 1 with the weapon pinned and the stage awaiting selection (prompt copy). While the stage is unchosen the pinned weapon survives difficulty/goal/boss changes; a class change drops it, warned.
- **Input changes:** swaps that stop being stage-legal are cleared (P4-S2 AC4, B106) with a visible rebuild notice and an advance warning where a swap exists (B108(e) H1).
- **Spec-silent readings ratified (B106):** defense quota = defense + survivability points; utility quota = all points; ArmorScore's survivability term = the survivability column only; profile damage bonuses by the weapon's own class (B94(6)); the gated track skips 0-point gated accessories.

4.1 **Main weapon:** rank class pool by DPP desc (ammo weapons scored with best recommendable ammo; none ⇒ weapon-only + disclosure). Rationale: "Highest estimated damage output of the N {class} weapons verified obtainable at your progress (est.)". Empty pool ⇒ designed empty slot with counts.
4.2 **Alt weapon:** next-ranked with different tags[0], else plain next, else empty with reason; hybrid alt must differ in damageClass.
4.3 **Armor (set-bonus-aware):** candidate = (set, class-eligible variant) where helmet+chest+legs all pass §3. ArmorScore = W_def·Σdefense + W_off·offensePts + W_mob·mobilityPts + W_surv·survivabilityPts using the goal's GOAL_WEIGHTS values. Set-bonus specials score 0 but are named. Rendered helmet = the class-eligible variant's.
4.4 **Accessories:** CATEGORY_TEMPLATE(G) quota list truncated/extended to SLOT_COUNT[D]:
boss: off,off,mob,def,off (+off) · max-damage: off×4,mob (+off) · exploration: mob,mob,util,def,off (+mob) · survivability: def,def,mob,off,def (+def) · mobility: mob×3,util,def (+mob) · balanced: off,def,mob,util,off (rotate).
Within category rank by (componentPts desc, hasSpecial desc, gatedBy.bosses.length asc, rarityRank asc, id asc). **Qualification rule:** needs ≥1 class-relevant point OR ≥1 special not tied to another class — zero-benefit items lose to honest empty slots. Constraints: no dupes; ≤1 wings; never co-equip direct combinedFrom/upgradesTo pairs (B53 direct links). Unfillable quota → top any-category candidate (disclosed) → empty with disclosure.
**Empty beats zero (B108(a), closes this section's intent gap):** an accessory with 0 counted points whose specials are all scoped to another class does NOT qualify — the slot goes honestly empty ("No accessory with a scored benefit for this class at this stage"). A special's class scope comes from SPECIAL_SCOPE_KEYWORDS, a small editorial keyword registry versioned APART from the constants (SPECIAL_SCOPE_VERSION 1, own changelog; both versions named in the weights assumption — B109): arrows/bows/ammo → ranged; yoyo(s)/melee speed (and unambiguous "melee … damage/weapons/attacks") → melee; mana/"magic damage/weapons/attacks" → magic; minion(s)/whip(s)/sentries/"summon damage/tag" → summon. Exactly one class matched ⇒ scoped; none or several ⇒ unscoped (conservative). A 0-point pick with unscoped specials may still fill a slot, but its card says it isn't scored ("not scored" / "its effects aren't scored" — B110; never implying another class would score it) and Step 3 lists every 0-point pick. On today's data no slot actually empties (0-point unscoped picks such as Copper Watch fill); the honest-empty path is fixture-tested (B109). A pinned accessory in a category-exhausted slot scores on any category (B109).
4.5 **Ammo:** pool = ammoStats.ammoClass match passing §3, rank by damage desc then id (today usually empty — honest; B68 derivation obligation). **Buffs:** rank by summed class-relevant points of granted buffs, fill ≤3 (BUFF_SLOTS), no repeated buff — the potion corpus landed with B70 (B90); a pick adding 0 counted points is named "not scored" (B108(a)). **Summon:** top minion staff by damage desc (NOT DPP — cast time ≠ minion rate); rationale notes "attack rate varies by minion AI — not estimated".
4.6 **Tie-break total order:** score desc → gatedBy.bosses.length asc → rarityRank asc (special tiers pinned after 11) → id asc.
4.7 **Gated track + easier alternative (P4-S3 AC3):** gated items that would outrank the pick (top 3/slot) group under "After you defeat {Boss}" with GateBadges; easier alternative = the top status-"yes" candidate of that slot ("Obtainable now: {item}"), else "No verified obtainable alternative at this stage". Never invented.
4.8 **Surprise Me:** seeded mulberry32; uniform draw per slot from the FULL legal pool honoring every constraint; randomness never relaxes legality; deterministic per seed; labeled "randomized from items verified obtainable at your progress". Ratified rules (B111 R2): a draw replaces fixed picks (swaps, a saved build's slots) — warned in advance ("Drawing replaces your N fixed picks…") and said afterwards; a slot swapped AFTER the draw keeps the user's pick (B113(e) M3). An input change re-draws under the same seed. An accessory drawn from any category is scored on all its points; the §4.4 qualification rule (B108(a)) holds for draws. The seed rides the URL (`?surprise=<seed>`, 1…2³²−1), so a link reproduces the draw; each drawn pick says it was drawn, not ranked.

## 5. Goal scoring (P4-S4)
5.1 **Components:** (1) estDamage: EDO = (perHit × (1+ΣdamagePct(C)/100) + ΣdamageFlat(C)) × hitsPerSec × speedFactor × critFactorTotal, where speedFactor = 1 + (Σattack-speed + Σmelee-speed·[C=melee])/100; critFactorTotal = 1 + (4 + weapon.critPct + Σcrit-pct(C))/100 (summon or classless ⇒ 1 — B17, B85(b)). Target-agnostic (defense 0). (2) defense: Σpiece.defense + Σdefense-flat; DR% separate labeled figure, never merged. (3) mobility: points + named uncounted specials. (4) survivability: defense-flat + 2·DR% + 2·life-regen + 0.25·max-life + named specials. (5) classSynergy (absolute 0–100): matched/(matched+mismatched)×100 over numeric points; breakdown itemizes every mismatch; flags: set bonus active, weapon class match, classless note.
5.2 **GOAL_WEIGHTS v1 (rows sum 1.0):** boss .45/.10/.15/.20/.10 · max-damage .70/.05/.05/.10/.10 · exploration .20/.10/.40/.20/.10 · survivability .10/.35/.10/.35/.10 · mobility .10/.10/.55/.15/.10 · balanced .25/.20/.20/.20/.15 (order: estDamage/defense/mobility/survivability/classSynergy).
5.3 **Normalization (share-of-both — B113(b), B114; supersedes the max-relative norm and the classSynergy exemption):** composites only for ≥2 builds. Each component — class synergy included — is split between the compared builds in proportion to their values: share_k(b) = 100·raw_k(b) / Σ_b′ |raw_k(b′)| (Σ 0 ⇒ all 0, flagged), so no build is pinned at 100 for being the larger — the "100.0 anchor" is removed everywhere. Symmetric exclusion: a component uncomputable for ANY build drops for ALL (disclosed). Weighted sum(b) = Σ included w·share / Σ included w — shown ONLY inside "How was this scored?", with each share's formula ("100 × 35 ÷ (35 + 20) = 63.6"). Exactly two builds ⇒ ONE signed difference in the existing "Draft − saved" grammar ("Under Survivability weights: saved +24.4 est."), computed from the displayed one-decimal sums; ties read "same". Single build ⇒ components-only. The same goal weights apply to every build, whatever goal each was made for.
5.4 **ScoreBreakdown props** (as built, `GoalComparison` in goals.ts): { goal, constantsVersion, builds[{ components[{id,label,raw,unit,dropped,scaled? (the share),scaledFormula?,weight,contribution?}], fit? (the weighted sum — disclosure-only) }], difference?{value, text, sign: −1|0|1, formulaText, assumptions[]} (exactly two builds — B113(b)), dropped[], zeroMax[] }; per-build profiles keep formulaText/uncounted[]/excluded (§5.1) — structurally no verdict slot; every numeric has EstimateLabel + populated AssumptionsTip; footer "weights v{N} — editorial constants".
5.5 **Profile bar references (P4-S3 AC2 — B113(a), B114; src/scoring/references.ts):** a Step 3 bar's reference must be PICK-INDEPENDENT — the highest value of that figure the search finds among gear verified obtainable for the user's stage, class, difficulty, target boss and tracked progress (the swap sheets' pools; owned-but-unverified gear left out). It reads only those inputs — never the goal, a pin, owned gear or a Surprise Me seed — so a bar can never compare a build with itself (banned) and a FULL bar must be EARNABLE, never the default. The reference is a real legal loadout (one armor set, ≤ the open accessory slots with no repeat, ≤1 wings, no direct combine/upgrade pair, ≤3 potions with different buffs) scored by the same §5.1 code, so swapping its gear in reaches it exactly; estDamage tries every weapon with gear chosen step by step (coordinate ascent), disclosed as "the highest found" — never "best". Each reference is est.-labeled with its own AssumptionsTip (how it was found, the gear that reaches it, its numbers) and drawn as a tick; no reference ⇒ no fill. Class synergy runs to 100 (no reference). Accepted (B114): legitimately-full bars where defaults genuinely hold the reference (thin data — the tick and copy carry it); Step 4's comparison bars run to the stated pair maximum.

## 6. Readiness factors (P5-S6/S7)
Loadout possession is asserted (gating never blocks analysis, only suggestions). All boss reads use statsByDifficulty[selected] — no cross-difficulty substitution ever; missing values remove the comparison + disclose. Factor shape: { id, title, lines[{tone: easier|harder|info|unknown, text, evidence: TypedRef[]}], computedFrom{used,total,unknownInputs[]} }. SummaryCard columns = union of easier/harder lines. No totals, grades, or outcome sentences.
**Precedence (B94(1)) — this section wins:** OWNED items always count in the analysis regardless of derived gating (ownership is user ground truth); B71's gated→never rule governs the suggestion/candidate pool (§3) only. An owned item whose usual sources need a boss not marked defeated adds an info-tone line in its factor naming those bosses (`owned.gated` copy, line id `<factor>.owned-gated`; per-gate lines shared across items) — honest, non-blocking, never in the summary columns. The Demon Heart slot stays EXISTENCE-gated on a tracked Wall of Flesh defeat (slot presence is world state, not item gating — B95, B69/Q3): while closed, its accessory isn't counted.
**Analysis-level assumption ids (B95):** `tracked-only`, `owned-gated` ("Gated items, counted"), `owned-unknown`, `demon-heart-closed` (split from `owned-gated`), `demon-heart`, `potions-active`; a slot holding an owned gated item reads "counted because it's in your loadout".
**Ratified readings (B94(6)):** dash-text detection; unmodeled mobility specials → unknown, not harder; no healing potion → harder; damage bonuses by the weapon's own class; "N of M points" synergy framing; line tones, not statuses (§1.6); the stage is context only — in the setup-pane note, not the analysis header (B96(c)); "yet" purged from the Unknown template. **Setup pane (B96(a), B97):** counts and names the user's ACTUAL marks; any "Both" nuance is a separate sentence.
**F1 Damage fit:** effPerHit = max(1, ⌊perHitWithPct − bossDefense/2⌋), then crit (variance not applied, disclosed); estDps = effPerHit × hitsPerSec × speedFactor × critFactorTotal. Template: "Your {weapon} is estimated at {estDps}/s (est.) after {boss}'s {def} defense.
